Enterspeed hosts three [Model Context Protocol](https://modelcontextprotocol.io/) servers. Point an AI client at one and it discovers a set of tools it can call on your behalf. You do not need to host anything yourself.

## Which one do you need?

| If you want to… | Use |
| --- | --- |
| Query content, indexes, and source entities in an environment | [Query MCP](/enterspeed/mcp-server/query-mcp/overview) |
| Understand or change how a tenant is configured, or author schemas | [Management MCP](/enterspeed/mcp-server/management-mcp/overview) |
| Ask questions about Enterspeed itself | [Documentation MCP](/enterspeed/mcp-server/documentation-mcp/overview) |

Query MCP and Management MCP are complementary — many people connect both, so an agent can read a schema, change it, and then query the result.

## How authentication works

Both tenant-facing servers are **passthrough proxies that hold no credentials of their own**. Every authorisation decision is made by the underlying Enterspeed API, never by the MCP server.

You connect to both servers by **signing in with your Enterspeed account**. You give your client the server URL, and it sends you to Enterspeed in a browser window where you sign in. The client keeps the resulting token. The steps for each client are under [Connecting a client](/enterspeed/mcp-server/query-mcp/connecting-a-client) for the Query MCP and [Connecting a client](/enterspeed/mcp-server/management-mcp/overview#connecting-a-client) for the Management MCP.

The Query MCP also accepts a scoped environment client key in an `x-api-key` header. Use one for an agent that runs unattended, because it cannot complete a browser sign in. Use one too when you want the connection fixed to one environment and one index scope. The Management MCP takes no key. You narrow a connection to it with parameters on the server URL instead, for example `?readOnly=true`. See [Limiting a connection](/enterspeed/mcp-server/management-mcp/overview#limiting-a-connection).

| Server | How you authenticate |
| --- | --- |
| [Query MCP](/enterspeed/mcp-server/query-mcp/overview) | Signing in with your Enterspeed account, **or** a scoped environment client key in an `x-api-key` header. |
| [Management MCP](/enterspeed/mcp-server/management-mcp/overview) | Signing in with your Enterspeed account. |
| [Documentation MCP](/enterspeed/mcp-server/documentation-mcp/overview) | Nothing — the documentation is public. |

### How long a sign-in lasts

A sign-in lasts **7 days** from the moment you sign in. Your client renews its access in the background every hour, so you do not notice anything during those 7 days. After that, the client asks you to sign in again. A scoped key on the Query MCP does not expire this way: it stays valid until you regenerate the environment client's key or delete the client.

### When someone leaves your organisation

**Remove the person from your Enterspeed tenant.** On the Management MCP that takes effect at once, because every request is checked against the tenant's members. On the Query MCP, the person can no longer select an environment, but a session of theirs that already has one selected keeps querying it. To end that straight away, regenerate the **Enterspeed MCP (sign-in)** environment client in each environment the person used, in the Management App. Their session stops within about five minutes, and everyone else selects the environment again the next time they query.

Disabling the person in your own directory is not enough on its own. If they sign in with your company's Microsoft account, disabling them there stops new sign-ins, but it does not end a connection they already have. Removing them from the tenant does on the Management MCP. On the Query MCP, regenerate the sign-in environment client as described above.

## Transport

Both tenant-facing servers speak **MCP Streamable HTTP** on the root URL, and nothing else. Choose the **HTTP** or **Streamable HTTP** transport in your client. The older SSE transport does not work: a client set to *SSE* fails on its first request with an HTTP 400 error. There is no `/sse` endpoint — always configure the root URL.
